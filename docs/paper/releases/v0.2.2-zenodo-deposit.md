## Why this is a manual deposit

The v0.1.0 record holds exactly two files — `main.tex` and
`diamond-framework-2026-10-11.pdf`. The GitHub→Zenodo integration archives a
zip of the repository, not a pair of named files, so v0.1.0 was uploaded by hand.
The same integration left **no** record for the v0.2.1 GitHub Release, which is
consistent with it not depositing this repository at all (the repository may be
enabled on the account but off for this repo, or that release was marked
pre-release).

**Do not do both.** If the webhook is later switched on, publishing a GitHub
Release would create a second deposit for the same version — two DOIs, one of
them unmaintained. Pick one path:

- **A — manual "New version" (recommended, used for v0.1.0).** You choose the
  two files and can review the metadata before publishing. The record is the
  paper.
- **B — GitHub Release.** Zenodo archives the repo zip at the tag. Convenient,
  but the record's primary file is a tarball rather than the 43-page PDF, and the
  `.zenodo.json` description then becomes the published text.

This checklist assumes **A**. Check
<https://zenodo.org/account/settings/github/> first: if `ilichb/diamond-framework`
is toggled **on**, either leave it on and use B, or leave it off and use A.

### Description (HTML, four paragraphs)

    <p>Proof-of-stake secures admission and deterrence with a single instrument,
    financial capital, and that is the source of its structural tension: high
    collateral requirements deter honest but capital-constrained validators, low
    requirements expose the network to Sybil attacks. The Diamond Framework
    replaces a fraction of the financial stake with verifiable, non-transferable
    reputation, so the admission barrier falls without claiming that the full
    Cost of Attack is preserved; that question is left open in the paper.</p>

    <p>This deposit is the frozen PDF snapshot of the manuscript, v0.2.2, with its
    source. v0.2.2 is a text release: it rewrites in the paper the three

## Order of operations

1. Record → **New version** on <https://zenodo.org/records/23268374>.
2. Delete the two inherited files, upload the two files above **in that order**,
   so the PDF is the primary file.
3. Paste the metadata, then **Reserve DOI** before publishing: the reserved DOI
   is what makes step 5 possible in one edit.
4. **Publish.**
5. Send the DOI here. The repository is then updated in one commit: `README.md`,
   `CITATION.cff`, `.zenodo.json`, `releases/README.md` and this file.
6. Only then tag `v0.2.2` and publish the GitHub Release, so the tag contains the
   DOI that names it.
