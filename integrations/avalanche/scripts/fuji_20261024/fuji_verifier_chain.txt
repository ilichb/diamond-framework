# `verifyThreshold` checks the epoch before the verifier (`AVIPRegistry.sol:427-431`):
# with no commitment posted, it reverts `UnknownEpoch` whether or not a verifier is
# installed. Installing the verifier is a precondition for a certified admission,
# not a demonstration of one. Exercising the path needs a posted epoch *and* a proof
# the key accepts, and the development key certifies nothing worth publishing.

# ---- what a reader should conclude ----
# 1. The `VerifierNotSet` gap described in the phase-2 record is closed without a
#    contract change: the deployed registry carried the proposal pair, and it now
#    carries the verifier. `pendingVerifier` and `verifierChangeEta` are back to zero,
#    so the state is the one a fresh deployment would have wanted, reached by delay.
# 2. The rotation is what the paper describes, and it has now been walked end to end:
#    propose, wait out `CHANGE_DELAY`, execute permissionlessly. Three transactions,
#    three blocks, and the second and third are 105,274 blocks apart. The guardian
#    cannot swap a verifier inside a block, and a compromised guardian is visible for
#    two days — the window that made this transaction a formality rather than a risk.
# 3. Replacing the development key with a ceremony key is the same operation —
#    `proposeVerifier` again with the ceremony verifier address, wait, execute. No
#    redeploy, no storage migration, 50,967 gas.
# 4. What is still open is not an address. It is a posted epoch and a proof the
#    development key accepts, and the key certifies nothing worth publishing. Point 1
#    closed the phase-2 record's gap; it did not close the admission path.
